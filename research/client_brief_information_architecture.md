# Client Brief Website — Information Architecture

## Purpose

The default website route will become an executive-facing client brief. It will retain the visual decisions approved in the Brand System but change the content hierarchy from *how the identity looks* to *what the client needs to approve, provide, and decide next*.

## Route plan

| Route | Role | Status |
|---|---|---|
| `/` | In-depth client brief: strategy, full September calendar, production requirements, domain status, recovery plan, and approval tracker | New default |
| `/brand-system` | Existing Optimum Physio Visual Brand System | Preserved as a distinct reference |

## Brief sequence

| Section | Client question it answers | Interaction |
|---|---|---|
| Brief cover | What is this document and what requires attention? | A domain-status callout links directly to recovery details. |
| Executive status | What is approved, what is blocked, and what is next? | Four concise status tiles distinguish content, brand, domain, and security-testing state. |
| September content plan | What will be published and when? | A ten-post calendar rail filters the full brief ledger. |
| Post library | What does each individual post need? | Expandable post cards show hook, audience, format, script/creative brief, CTA, and production note. |
| Content system | Why does the calendar follow this sequence? | Pillar mix, campaign flow, and caption/CTA framework are shown in succinct working cards. |
| Production and approvals | What does the clinic need to supply before production? | A live progress panel turns client inputs into a reviewable checklist. |
| Website and domain | Why could the security test not proceed, and what is required? | A plain-language technical status panel separates verified findings from the recommended recovery path. |
| Decision path | What must be agreed before launch and testing? | A four-step recovery route makes ownership, domain configuration/purchase, implementation, and authorised test readiness explicit. |

## Key content and safety decisions

The current brand-system approval interaction will be replaced by an operational client-brief approval panel: service/menu confirmation, final clinician details/scripts, patient consent, contact/booking details, accessibility assets, clinical review, and domain recovery decision. Individual post briefs retain the exact source content and use the same medically safe boundary language from the supplied strategy. Domain and security content will not claim that a security test was conducted; it states that it could not proceed because the public domain was unreachable at the time of the supplied audit.
